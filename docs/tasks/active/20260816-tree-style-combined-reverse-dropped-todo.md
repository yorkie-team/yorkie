# Tree Style: a combined reverse's removal half is dropped on execute

**Created**: 2026-08-16

Found while building the Tree `Style` reverse operation
(`docs/design/undo-redo-go-port.md`, Task 16), refiled out of
`docs/tasks/active/20260816-remote-redo-replica-divergence-todo.md` because
this defect is **convergent** (every replica drops the removal identically),
not divergent the way that document's other entries are — filing it there
mislabeled it and buried it behind entries with a different failure shape.

## Problem

`TreeStyleOperation.execute` (`tree_style_operation.ts:127-158`) is:
```ts
if (this.attributes.size) {
  ...
  [pairs, changes, diff, prevAttributes, newAttrKeys] = tree.style(...)
  ...
} else {
  const attributesToRemove = this.attributesToRemove;
  ...
  [pairs, changes, diff, prevAttributes] = tree.removeStyle(...)
  ...
}
```
an **if/else**. `StyleOperation.execute` (Text's twin,
`style_operation.ts:125-166`) is **two independent `if` blocks** — one for
`attributesToRemove`, one for `attributes`, both run whenever their field is
non-empty. `CRDTTree.style`/`removeStyle` and `CRDTText.setStyle`/
`removeStyle` take independent parameter lists (verified — neither takes the
other's parameter), so nothing requires the exclusivity; it is purely the
`execute` method's own branch shape.

This makes no difference on a forward call — `json/tree.go`'s `Tree.Style`
and `Tree.RemoveStyle` (mirroring JS's json-level callers,
`packages/sdk/src/document/crdt/tree.ts`) always build an operation with
exactly one field populated. It surfaces only when `execute` runs a
**combined reverse** — one carrying both a restore (`attributes`) and a
removal (`attributesToRemove`) at once. On JS's if/else, the `attributes`
branch runs (restoring the existing key) and the `else` branch — the
`attributesToRemove` removal — never runs at all. The key that should be
removed is left in place, on every replica that executes that reverse: the
undoing client's own redo, and any peer.

### This is reachable in ordinary single-client editing, not just theoretically

JS's own reverse builder really does emit combined ops. `crdt/tree.ts:1546-
1555` splits the keys requested by a single `Style` call, on a single node,
into `prevAttributes` (existed before, restore) and `newAttrKeys` (did not
exist, queue for removal) — the same split `crdt.Tree.Style`'s `PrevAttr`
capture makes in Go (`pkg/document/crdt/tree.go`, Task 14). So any `Style`
call that mixes restyling an existing attribute with adding a brand-new one
in the same range produces a combined reverse, e.g. bold already `"true"`,
style with `{bold: "false", italic: "true"}`. This needs no concurrency —
ordinary single-client editing hits it — which is the property that
distinguishes it from most of the entries in the replica-divergence
document, and why it was filed separately here.

### Provenance

`git log` on both files pins this precisely. Text's independent-if shape was
introduced by PR #1174 ("Add undo/redo support for Text.Style operations").
Tree's undo/redo support followed two months later in PR #1221 ("Add
undo/redo support for TreeStyleOperation"), whose commit message says the
reverse-op logic follows "Text's StyleOperation pattern" — and the
reverse-*building* code (the final `if (reversePrevAttributes.size > 0 &&
reverseAttrsToRemove.length > 0) ...` block) does match Text's exactly. But
the surrounding forward-execute branch was left as Tree's pre-existing
if/else rather than being converted to Text's independent-if shape
alongside it. The combined-reverse constructor `TreeStyleOperation` now
hands out is a shape its own `execute` cannot fully replay — an oversight
introduced by #1221 copying half of #1174's pattern, not a deliberate design
difference between Text and Tree.

## Why this must be fixed in both SDKs together, not patched in Go alone

Go's `operations.TreeStyle.Execute` (`pkg/document/operations/tree_style.go`)
ports this if/else shape as-is, per this port's rule against fixing a defect
the JS SDK still has. The reasoning for *why* that rule applies here, and
applies more strongly than in most of the divergence document's entries:

**Go is not just a peer SDK, it is the server.** `change.Execute`
(`pkg/document/change/change.go`) replays every operation — including a
combined `TreeStyle` reverse arriving from a JS client's undo — through
these same methods, and server snapshots are built from that replay. If Go
unilaterally adopted the independent-`if` shape while JS keeps the if/else,
a combined reverse — whether generated by a Go client or a JS client's undo
— would remove the key on the server (and on any Go replica) while every JS
replica keeps it. That converts a uniform, convergent correctness bug
(everyone silently keeps a key that should have been removed) into
**permanent server-versus-client state divergence** (the server and Go
clients disagree with every JS client, forever, with no reconciliation
path). Uniformly wrong is recoverable by a coordinated fix later; divergent
is not. This is why the fix must land in both `yorkie` and `yorkie-js-sdk`
together, or behind a version gate — never as a one-sided Go patch, even
though the "correct" independent-if shape is a small, obvious-looking
change.

## Persisted-data note

A JS-originated combined `TreeStyle` reverse, if it was persisted (synced to
the server, stored in a change log, or captured in a snapshot) **before**
this port's `fromTreeStyle` fix (`api/converter/from_pb.go`, Task 16) was
applied, was decoded as a removal-only operation at the time (the pre-fix
exclusive-decode bug: `AttributesToRemove` took priority and `Attributes`
was silently dropped). After the fix, decoding the same bytes now correctly
recovers both fields and replays as attributes-branch execution — a restore,
not a removal, given this document's if/else finding above. So a snapshot or
change log materialized under the *old* decode can disagree with a *fresh*
replay of the same underlying change, for any historical combined `TreeStyle`
reverse. The new decode behavior is the correct one, and this is the same
trade the Text `fromStyle` fix already accepted for the identical wire-decode
shape — but it should not be rediscovered as a mystery during a future
compaction or snapshot-rebuild investigation. No migration is planned here;
this is a note for whoever next touches snapshot/change-log compatibility
for this operation.
